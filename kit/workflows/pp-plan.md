# Plan

1. Read the operating manual and pp-orchestrator persona. Run `product-planner status --json`, inspect the repository and existing planning docs. Resume completed planning work rather than starting over. Set phase to planning. If this is already a build, preserve the approved plan and ask whether the requested change is new scope before replacing it.
2. Mark setup in_progress. In focused question batches, collect product goal, users, problem, business model, MVP boundaries, success metrics, platform, budget, deadlines, technical constraints, existing code/assets, design style and accessibility. Reuse the user's supplied answers. Ask about research, supplied sources/competitors and web access: native tools, built-in CLI, optional free MCP/SearXNG, or no web. Run `research options` if useful; agree any installation before doing it. Ask about optional marketing, keyword/vector project memory, commit-per-task, push/deployment authorization and dashboard sections/auto-open. Do not require paid services. Record options with state set; record deployment/push scope in decisions.md. Mark setup done.
3. Use pp-analyst to write concept.md and initial risks.md from the interview. Record product name/tagline/summary with state product. Mark concept in_progress then done. Resolve material unknowns now.
4. If research is enabled, mark research in_progress and use pp-researcher to discover competitors, pros/cons, market and UX evidence with sources. Set webAccess to native, cli or none based on actual availability. If no web, work from supplied references and record limits. Mark research done when the agreed scope is complete, otherwise record the limitation explicitly. If declined mark skipped.
5. Use pp-pm for prd.md, then pp-ux-designer for ux.md. Mark each step in_progress/done. If marketing is requested use pp-marketer for marketing.md, otherwise mark skipped. Independent documents may run in parallel only after their inputs exist and output ownership is clear.
6. Use pp-architect for architecture.md, decisions and technical risks. Resolve required accounts, integrations, credentials, local testing paths and deployment scope before build. Mark architecture done.
7. Use pp-planner to write plan.json and roadmap.md. Import using `product-planner task add --file .product-planner/plan.json` and run `product-planner task validate`. Audit coverage of all must-have requirements, dependency order and verifiable acceptance. Mark tasks done only when validation succeeds.
8. If memory was chosen, run memory index; install the vector option only if agreed. Generate `product-planner dashboard`. Include any requested custom data in dashboard/*.json. Mark handoff in_progress. Present a single whole-plan review: MVP, UX/UI direction, evidence and competitor gaps, stack, epics/tasks, assumptions, risks, deferred roadmap and dashboard path. Ask for approval or revisions. This is the only approval gate; questions earlier are requirements gathering. Do not start build before approval.
9. Apply requested revisions, synchronize docs/tasks and validate again. On approval mark handoff done and run `product-planner state phase build` (opens the dashboard unless disabled). Continue directly with pp-build unless the human asked to stop after planning. Commit only the intended project files if agreed; never push without authorization.
