# Plan

1. **Orient.** Read the operating manual and pp-orchestrator persona. Run `product-planner status --json`, inspect the repository and existing planning files (concept.md, features.json, decisions.md). Resume completed work instead of starting over; never re-ask an answered question. Set phase to planning. If a build is already under way, keep the approved plan and ask whether the request is new scope before replacing anything. For an existing codebase follow `guides/existing-products.md` and write baseline.md before asking questions.
2. **Interview (setup + concept).** Mark setup and concept in_progress. Use pp-analyst and follow `guides/interview.md` exactly: draft first, then at most 3 rounds of at most 5 multiple-choice questions with a recommended answer each. Round 1 confirms the track (`state set options.track quick|standard|existing`), user, problem and platform. After round 1 record a working name with `state product --name "…" --tagline "…"` so the dashboard is labelled while planning continues. Round 2 proposes the feature list for the user to accept, defer or reject, then fills gaps in the accepted MVP features (flow, data, roles, edge cases, integrations, acceptance). Round 3 covers constraints and the setup options in one batch: research and web access, browser access (`guides/browser-policy.md`: use the host's own browser, otherwise ask before `browser setup`), memory, models per agent (`state set models.<agent> <id>`), commit/push/deploy permission and dashboard preferences. Save answers as you go: features with `product-planner feature add|set`, options with `state set`, preferences and assumptions in decisions.md. Mark setup done.
3. **Concept brief.** Run `product-planner feature check` until it passes (or move what stays unknown into assumptions). Write concept.md with the concept brief template and initial risks.md, record `state product --name --tagline --summary`, and show the brief for one confirmation ("Is this the product?"). Apply corrections, then mark concept done.
4. **Research** (if enabled; in the quick track only when asked). Mark research in_progress, use pp-researcher for competitors, market and UX evidence with sources, and set webAccess to native, cli or none according to what actually worked. New feature ideas from research go into features.json as `proposed` with `source: research` and are put to the user in the final review, not as new questions now. Mark done, or skipped if declined.
5. **Requirements and design.** Use pp-pm for prd.md, tracing each FR to a feature ID. Standard/existing tracks: pp-ux-designer writes ux.md. Quick track: put UX direction in a prd.md section and mark ux skipped. Use pp-marketer only if marketing was requested, otherwise mark skipped. Then pp-architect writes architecture.md (short in the quick track), decisions and technical risks, and settles accounts, credentials, local test paths and deployment scope. Mark each step done.
6. **Tasks.** Use pp-planner to write plan.json (every task lists the `features` it delivers) and roadmap.md (one `##` section per release; Next/Later features go here). Import with `product-planner task add --file .product-planner/plan.json`, then run `product-planner task validate`, which also fails when an accepted MVP feature has no tasks. For existing products preserve completed tasks, use unused IDs and reconcile revisions explicitly. Mark tasks done only when validation passes.
7. **Final review (the only approval gate).** If memory was chosen run `memory index`. Run `product-planner dashboard`. Mark handoff in_progress and present the whole plan once: concept brief, feature table (MVP / next / later, with assumptions), UX direction, evidence and competitor gaps, stack, epics and tasks, risks and the dashboard path (plus baseline gaps for existing products). Ask for approval or changes. Do not start building before approval.
8. **Handoff.** Apply requested changes, keep features, docs and tasks in sync, and validate again. On approval mark handoff done and run `product-planner state phase build` (opens the dashboard unless disabled). Continue with pp-build unless the user asked to stop after planning. Commit only intended project files if agreed; never push without authorization.
