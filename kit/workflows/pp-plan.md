name: pp-plan
description: Plan a product or feature from an idea - short multiple-choice interview, feature list, research and full plan before one final approval. Use when the user describes something to build and no approved plan covers it.
---

# Plan

1. **Orient.** Read the pp-orchestrator persona (the kit README is reference only). Run `product-planner status --json`, inspect the repository and existing planning files (concept.md, features.json, decisions.md). Resume completed work instead of starting over; never re-ask an answered question. Set phase to planning. If a plan was already approved, do not start over: use pp-replan for changes to it. If the request is small, precisely specified and authorizes building, with no platform or regulatory concern, use pp-direct instead. Determine new versus existing from repository contents, not whether Planner was just installed. For an existing codebase follow `guides/existing-products.md`: inventory repository files, learn from its documents and implementation, and save discovery.md and baseline.md before asking questions. For a new product follow the interview to resolve missing requirements and persist answers and plans under `.product-planner/`; never leave the plan only in chat. All planning deliverables below are relative to `.product-planner/`, not the repository root or `.product-planner/kit/`.
2. **Interview (setup + concept).** Mark setup and concept in_progress. First save the user's request verbatim to `.product-planner/request.md`. Use pp-analyst and follow `guides/interview.md` exactly (skip any question the request already answers; a precise request may need no questions): draft first, then rounds of at most 5 multiple-choice questions with a recommended answer each, continuing until the readiness gate passes (no fixed round limit; "use your recommendations" ends it). `product-planner request list` numbers the request statements R1, R2, …; every one must end up mapped to a feature's `requests` or to `notFeatures` with a reason. Round 1 confirms the track (`state set options.track quick|standard|existing`), user, problem and platform. After round 1 record a working name with `state product --name "…" --tagline "…"` so the dashboard is labelled while planning continues. Round 2 proposes the feature list for the user to accept, defer or reject, then fills gaps in the accepted MVP features (flow, data, roles, edge cases, integrations, acceptance). Round 3 covers constraints, the quality-profile questions (`profile catalog` lists them; `profile detect` shows repository signals: platform or marketplace, where users are, personal data, payments) and the setup options in one batch. Select the profile with `profile set <ids> --because "…"` (or record "no profile applies" in decisions.md). Setup options: research and web access, browser access (`guides/browser-policy.md`: use the host's own browser, otherwise ask before `browser setup`), memory, the AI tools, providers and plans available (record with `models available <ids…>`; do not ask the user to pick models per role), commit/push/deploy permission and dashboard preferences. Save answers as you go: features with `product-planner feature add|set`, options with `state set`, preferences and assumptions in decisions.md. Mark setup done.
3. **Concept brief.** Run `product-planner feature check` and `product-planner request list` until every feature is decided and every request statement is mapped (or move what stays unknown into assumptions); ask further rounds for real gaps. Write concept.md with the concept brief template and initial risks.md, record `state product --name --tagline --summary`, and show the brief for one confirmation ("Is this the product?"). Apply corrections, then mark concept done.
4. **Research and recommendation** (market research if enabled, in the quick track only when asked; quality-profile verification whenever a profile is selected). Mark research in_progress. Use pp-researcher for competitors, market and UX evidence with sources, and set webAccess to native, cli or none according to what actually worked. If the product's platform or a law that applies is not in `profile catalog`, create a profile for it (`profile new <id>`), fill it from the official documentation, `profile validate` it and select it; offer `profile save <id>` at the review so other projects can reuse it. For each selected quality profile, check its official sources for current requirements and versions and record it with `product-planner profile verify <id> --sources "…" --note "…"`; adjust gates (`profile gate`) where the sources differ, with the reason. When a decision depends on outside knowledge (approach, libraries, services, platform limits), write a recommendation in research/recommendation.md from `templates/recommendation.md`: 2–3 options with trade-offs and sources, and one recommendation. Then confirm the user flow and recommended approach with the user in one short message (the main journey as numbered steps, the recommendation, and what it rules out) before architecture is written; apply corrections. New feature ideas from research go into features.json as `proposed` with `source: research` and are put to the user in the final review, not as new questions now. Mark done, or skipped if declined.
5. **Requirements and design.** `product-planner plan profile` lists the documents and roles for the chosen depth. Standard/existing tracks: use pp-pm for prd.md, tracing each FR to a feature ID; pp-ux-designer writes ux.md; then pp-architect writes architecture.md, decisions and technical risks, including a "Quality and compliance profile" section with one decision per non-legal gate that names its id (data location, encryption, consent and deletion paths, platform conventions, tooling and levels). Quick track (or `options.planningDepth quick` on an existing product): one focused pass writes a single plan.md from `templates/quick-plan.md` with `## Requirements`, `## UX`, `## Architecture`, `## Risks` and `## Roadmap` sections, instead of separate prd/ux/architecture/risks/roadmap files; briefs and `check` read those sections; put the quality and compliance decisions under `## Architecture`. Keep exact interfaces, values and error cases from request.md and trace each FR to a feature ID; security, migrations or broad API changes still get deeper analysis. Use pp-marketer only if marketing was requested, otherwise mark skipped. Settle accounts, credentials, local test paths and deployment scope. Mark each step done (on the quick track mark prd, ux and architecture done once plan.md covers them).
6. **Tasks.** Use pp-planner to write plan.json with `features` (with `requests`), `notFeatures`, `epics` and `tasks`. Every task lists the `features` it delivers, its `risk`, the `gates` it implements or checks (tool setup in the first epic, controls as their own tasks), the repository paths it will change in `writes` and the paths it depends on in `sources`, so build can batch disjoint work and detect stale evidence. Epics are increments that each deliver a working vertical slice. Also write and roadmap.md (one `##` section per release; Next/Later features go here; on the quick track use plan.md's Roadmap section). Import everything in one step with `product-planner plan import --file .product-planner/plan.json`, which runs `product-planner check` (no model needed): it fails on graph errors, unready features, MVP features without tasks, unmapped request statements and quality gates without an architecture decision or task, and warns about requirement IDs no task references, unverified profiles, vague acceptance wording and unfilled template sections. Fix every error and every warning you can; justify the rest in decisions.md. For existing products preserve completed tasks, use unused IDs and reconcile revisions explicitly. Mark tasks done only when validation passes.
7. **Final review (the only approval gate).** If memory was chosen run `memory index`. Run `product-planner dashboard`. Mark handoff in_progress and present the whole plan once: concept brief, feature table (MVP / next / later, with assumptions), UX direction, evidence and competitor gaps, stack, epics and tasks, the quality and compliance profile ("these checks and laws apply, because …", with the gates and the items that need legal review), the recommended model for each task with its reason, reviewer and price basis (`product-planner models recommend`; the user can accept or change any line), high-risk tasks (`risk: high`) that the approval covers, risks and the dashboard path (plus baseline gaps for existing products). Ask for approval or changes. Do not start building before approval. Exception: on the quick track, when the interview needed no questions and the user's request explicitly asked you to build, treat that request as approval; say so in one line, record it in decisions.md and continue (the user can still stop you).
8. **Handoff.** Apply requested changes, keep features, docs and tasks in sync, and validate again. On approval run `product-planner models apply` (or `models auto` when the user wants each build task delegated to sub-agents), then `product-planner plan approve --reason "<who approved and how>"`: it requires a passing check, marks the remaining planning steps, records a lock snapshot of the request, scope and tasks (later changes go through pp-replan) and moves to build (opening the dashboard unless disabled). Continue with pp-build unless the user asked to stop after planning. Commit only intended project files if agreed; never push without authorization.
