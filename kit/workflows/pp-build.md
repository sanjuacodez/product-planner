description: Build the approved plan task by task with QA and dashboard updates, without stopping for questions. Use when the user says build, start building or next task after approval.

# Build

1. Read the pp-orchestrator persona and `product-planner status --json` (the kit README is reference only). Require an approved plan (planning.handoff = done, recorded by `plan approve`); if absent return to pp-plan's final review. If a quality profile is selected (`product-planner profile show`), its gates apply to the tasks that list them. Read the product concept and task graph; retrieve task-specific requirements, UX, architecture and decisions through the brief, then read missing evidence as needed. Follow `guides/execution.md` for models, ownership and delegation. Validate the plan before execution. Respect the user's existing deployment/push/commit choices and host permissions.
2. **Delegated mode** (`options.delegateTasks` true, set by `product-planner models tiered`; check with `product-planner models show`): the coordinator keeps a short context and does not implement. For each task: start it, then give the pp-developer sub-agent the `task context T#` brief, owned paths and acceptance (it writes tests with the code and runs the full suite, and returns changed paths, results and decisions); then give the pp-qa sub-agent the brief, the changed paths and the report template path (it runs the suite and the task's gates and fills the report). The coordinator reviews the evidence, runs `task complete`, and moves on, without re-reading the work in full. Use each task's requested `model` for the developer sub-agent and its `reviewModel` for QA review (set by `product-planner models apply`): pass them per call when the host's agent tool accepts a model, otherwise the role's agent file applies. When the tool offers several providers, run batch slots on the providers the router chose. Tasks with `risk: high`, or returned by QA, run on the strongest available model: pass a model override when the host allows, otherwise implement them in the coordinator session. If the host has no sub-agents, work sequentially as below.
3. Recover in_progress and review tasks first: inspect their files and notes, adopt or delegate their assigned persona, and finish implementation/QA rather than leaving them orphaned. Recheck blocked tasks whose external cause may have changed; unblock only with evidence. Keep one coordinator writing shared state. Use `task ready --json` and `guides/execution.md` to delegate independent tasks concurrently when the host allows it, with exclusive output paths and a default cap of two active build tasks. Serialize overlapping or uncertain ownership; workers never write shared planner state.
4. Run `product-planner task next` for sequential work, or `product-planner task batch --json` for a proposed parallel batch: it selects ready tasks whose declared `writes`/`sources` do not overlap active or selected work, up to `options.maxConcurrentTasks`, and lists skipped tasks with reasons (tasks without declared `writes` always run sequentially). The batch is a proposal; it starts nothing. After `task start`, run `task capture T#` to snapshot the planning documents and declared source/write paths; the brief then reports whether that evidence is fresh or which files changed (`task freshness T#`). Run `product-planner task context T#` for a compact brief (acceptance, features, requirement lines, dependencies, decisions) and read further documents only for what the brief does not answer. For existing products read baseline.md and lessons.md, then inspect current affected source and available dependency evidence; refresh stale provider results or fall back to direct inspection. Start with `task start T# --agent <persona> --model <model-id>`, where model-id is the AI model actually running that persona in this session (the identifier or name your host shows; omit only if the host does not reveal it). Pass the same `--agent`/`--model` pair on every later transition so the dashboard shows which agent and model did the work. Resolve requested models and record actual models as described in `guides/execution.md`. Delegate with a concrete brief (goal, product context, input paths, exclusive output paths, acceptance criteria); otherwise announce and adopt the pp-<agent> persona. Implement fully and record decisions through the coordinator. Where behaviour is testable, write the automated tests first from the acceptance criteria (and the matching rules in request.md), one or more per criterion, named after it, and see them fail before implementing.
5. For delegated work the coordinator collects outputs, checks the combined diff and runs relevant batch integration checks before dependent work is released. Use pp-qa to verify every acceptance criterion. Run the full test suite once after the task's changes (the definition of done), and `product-planner profile run <gate ids>` for the automated gates the task lists; fix new findings in this task rather than deferring them (on existing products the rule is no new findings beyond the recorded baseline). `task policy T#` states the checks the task's risk requires (every task: acceptance, the test suite and its gates; medium adds an independent reviewer; high or a task returned by QA three times adds integration and a security/data-integrity review). If QA finds defects, fix and recheck; do not mark done because time or context is low. Record actual checks/results using `--note`, mapping each acceptance criterion to its evidence (test name, command or manual check). If the CLI warns that QA returned the task repeatedly, change approach or block it with a precise reason instead of looping. When `options.requireVerification` is true (the default for new projects), complete the task with recorded evidence: `product-planner task verify T# --template --out .product-planner/verification/T#.report.json`, fill every row (status `pass`, concrete evidence) plus the required reviewer and checks (the suite result, each `gate G-…` result), then `product-planner task complete T# --file .product-planner/verification/T#.report.json --agent qa --model <model-id>`, which moves the task through review, records the verification and marks it done in one step. The CLI rejects missing, unknown or unverified criteria and refuses if verified files changed since; verify again after any fix. When the CLI reports that an epic is complete, run the increment's integration checks (the full suite and the journeys the epic delivered) and record them with `product-planner epic review E# --evidence "…"`. After QA, record reusable verified findings in lessons.md using the template; include source/task/check evidence. Refresh the affected baseline and enabled document memory when they change. Update requested dashboard data. If commitPerTask is true and this is a git repo, commit only intended task files and state/docs; avoid including unrelated user changes. Never push unless already authorized.
6. If blocked, try reasonable remedies within the approved scope. Record a precise reason with `task block T# --reason "..."`, including missing prerequisite and what resolves it. Choose other ready work without interrupting the human. Do not ask routine design/implementation questions during build: document reasonable decisions. Host-enforced approvals and the user's explicit steering still apply.
7. Repeat until ALL_DONE or ALL_BLOCKED. NONE_READY means inspect active/review work and the dependency graph, not success: resume active tasks, repair invalid dependencies, or explain transitive blockers. Do not wait on a todo task whose prerequisite is blocked. For ALL_BLOCKED provide a consolidated list of unresolved prerequisites and the dashboard path.
8. On ALL_DONE run final integration QA for the main journeys, setup documentation and relevant checks, then the **acceptance audit**: pp-qa re-reads request.md and every accepted MVP feature, runs the full test suite and `product-planner profile run` (all automated gates), and records the result: `product-planner audit template --out .product-planner/audit-report.json` lists one row per request statement (R#), accepted MVP feature criterion and non-legal quality gate, plus the legal items for review; fill each row with evidence (status `pass`) and `integration` with the full-suite command and result, then `product-planner audit check --file .product-planner/audit-report.json`. It also requires every task done with verification recorded at completion and, with more than one epic, every increment reviewed, and writes acceptance.md (including the legal-review list, which is never marked passed). A row that cannot pass becomes a corrective task; continue until the audit passes. Run `product-planner check`. If defects remain, create concrete corrective tasks and continue. Once all checks pass set phase done (`state phase done` refuses without a current passing audit when verification is required; any later source, task or concept change makes the audit stale), update roadmap/risks and any enabled memory, regenerate dashboard and report delivered behavior, verification and remaining limitations. An empty task list requires returning to planning, not declaring a finished product.
