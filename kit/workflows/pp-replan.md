# Replan

A replan changes an agreed plan without starting over. Completed work is kept; only what the change touches is revisited.

1. **Orient.** Append the user's change request verbatim (dated) to request.md. Read the manual, `product-planner status --json`, features.json (`feature list`), tasks (`task list`), decisions.md and the latest log. If no plan has been approved yet, this is ordinary planning: continue pp-plan instead. If the request does not change agreed scope (a bug fix, copy change, or something already covered by a task's acceptance criteria), do not replan: do the work or note it on the task.
2. **Park the build safely.** If a task is in_progress and the change does not affect it, finish it through QA first. If the change does affect it, return it to todo with `task reopen T# --note "paused for replan"` so nothing is left half-done. Do not start new tasks until the replan is approved.
3. **Restate the change and its impact** before asking anything. List: features added, changed, deferred or rejected (by ID); tasks affected (not started, in progress, done); documents and sections affected (concept brief, prd.md, ux.md, architecture.md, roadmap.md); and new risks, dependencies, accounts or costs. Read the affected source code for existing products.
4. **Ask only about the change.** At most one round of at most 5 multiple-choice questions with recommended answers, following `guides/interview.md`. Everything else becomes a recorded assumption.
5. **Propose, do not apply yet.** Write nothing to features.json, tasks.json or the documents before approval, so a build session cannot pick up unapproved work. Show one change summary: features +added ~changed −removed/deferred, tasks +added ~updated −removed (with titles, dependencies and acceptance), documents and sections to edit, effect on remaining work, and risks or costs. Ask for approval or adjustments. This is the only gate for the replan; apply adjustments to the proposal and re-show only what changed.
6. **Apply after approval.**
   - Scope: map the new request statements (`request list`) to features' `requests` or `notFeatures`. New features with `feature add` (new F IDs, `source: user`, status accepted); changed features with `feature add` using the same ID; removed or postponed features with `feature set F# status rejected|deferred` and `feature set F# release Next|Later`. Run `feature check`. Update the concept brief only if the MVP or primary user changed.
   - Documents: edit only the affected sections of prd.md (keep FR IDs; add new ones, mark dropped ones as removed with the replan date), ux.md, architecture.md and roadmap.md, or the matching plan.md sections on the quick track. Never rewrite unaffected documents.
   - Tasks: not started but different → `task update T# --json '{…}' --note "replan: …"`; not started and no longer needed → update dependents, then `task remove T# --reason "replan: …"`; done work that must change → keep it done and `task add` a follow-up that depends on it; new work → `task add` with new IDs and `features` set. If the change brings a new platform, market or kind of personal data, update the quality profile (`profile set … --because "…"`, `profile verify`), add the architecture decisions and tasks for the new gates. Then `product-planner check` and fix what it reports.
7. **Record and continue.** Append a dated "Replan" entry to decisions.md (what changed, why, what was kept), run `product-planner log "replan: <summary>" --agent orchestrator`, regenerate the dashboard and commit the plan files if commits are agreed. Record the approval with `product-planner plan approve --reason "replan approved: <summary>"`, which re-locks the plan and sets phase build; continue with pp-build unless the user asked to stop. The appended request and changed tasks make any earlier acceptance audit stale; pp-build runs it again at the end. If it was still in planning, continue pp-plan from the earliest affected step.
